# PRODIFY: Comprehensive Product Specification & Functional Requirements

This document establishes the absolute functional, behavioral, and UI/UX requirements for Prodify. It serves as the single source of truth for features, state interactions, schemas, and AI behaviors. All code generated by AI agents must strictly comply with the designs detailed herein.

---

## 1. Product Overview & User Workspace Modes
Prodify is an intelligent, self-optimizing productivity workspace web application. The core user experience rotates around a highly responsive workspace dashboard running one of two distinct operational tracking methodologies chosen by the user upon workspace creation.

### Feature 1A: Structured Goal Mode (Model A)
* **Objective:** For users tracking toward a hard deadline with an absolute hourly requirement (e.g., studying 21 hours over a 7-day exam prep timeline).
* **Core Behavioral Logic:** If a user underperforms or skips a day, the system automatically recalculates and inflates the daily required time for the remaining days to ensure the goal is met.
* **Mathematical Velocity Recalculation:**
  $$T_{\text{daily}} = \frac{T_{\text{remaining}}}{D_{\text{remaining}}}$$
  Where $T_{\text{remaining}}$ is the remaining target hours left in the workspace goal, and $D_{\text{remaining}}$ is the number of remaining calendar days until the target deadline date. This evaluation fires every night at 00:00 AM server-time.
* **UI Indicator:** A prominent "Required Daily Velocity" ticker that dynamically shifts color (Green to Yellow to Dark Red) as the calculated daily required hours scale upward due to skipped sessions.

### Feature 1B: Flexible Tracking Mode (Model B)
* **Objective:** For continuous, open-ended development, learning, or working without a hard chronological calendar deadline (e.g., open-ended full-stack project building).
* **Core Behavioral Logic:** Tracks cumulative logged hours chronologically. Focuses entirely on calculating rolling averages, highlighting peak productivity windows, and running baseline anomaly alerts to detect creeping exhaustion.

## 2. Deep Feature Specification: The Pomodoro Finite State Machine
The core timer element inside the active workspace layout must be driven by an explicit, deterministic Finite State Machine (FSM) managed inside a frontend Zustand store. 

### FSM States & Transitions
* `IDLE`: Timer is set to its baseline duration (Default: 25 minutes). UI shows a prominent "Start Focus Session" action button.
* `FOCUS_RUNNING`: Ticker counts down toward zero second-by-second. The visual telemetry canvas and tab visibility observers are fully armed and polling data.
* `FOCUS_PAUSED`: Ticker freezes. A text field forces the user to manually select a reason for pausing (e.g., "Restroom", "Urgent Call", "Interruption") before they can click "Resume". Telemetry gathering is suspended during explicit manual pauses.
* `BREAK_RUNNING`: Ticker counts down a short rest block (Default: 5 minutes). Telemetry is active but ignores eye closures or tab switches.
* `BREAK_PAUSED`: Rest ticker freezes.
* `SESSION_COMPLETED`: Ticker hits zero. The frontend instantly fires an async HTTP `POST` request to `/api/sessions/complete` to persist the block, plays a clean audio notification, and forces transition to `BREAK_RUNNING`.

## 3. Deep Feature Specification: The Dual-Vector Telemetry & Enforcement Loop
The telemetry engine captures behavioral signs of distraction and fatigue, executing automated UI-blocking enforcement penalties if thresholds are violated.

### The Visual Telemetry Engine (MediaPipe Face Mesh)
* **Implementation:** Client-side `@mediapipe/tasks-vision` loaded directly into the browser viewport runtime.
* **Metric Calculation (PERCLOS):** The frontend tracks facial landmarks around the eye vectors to assess eyelid closeness over a sliding 60-second window.
  $$\text{PERCLOS} = \frac{\text{Frames where Eyelid Closure} \ge 80\%}{\text{Total Captured Frames in Window}}$$
* **Fatigue Trigger:** If $\text{PERCLOS} \ge 0.15$ (meaning eyes are closed at least 80% of the way for more than 15% of the rolling minute), a fatigue warning flag is set to true.

### The Contextual Telemetry Engine (Browser Sandbox Tracking)
* **Implementation:** Dual observers using the HTML5 Page Visibility API and the window blur interface.
* **Distraction Trigger:** The instant `document.visibilityState === 'hidden'` or `window.has_focus === false`, an unexcused distraction event is initialized.

### The 15-Second Enforcement Matrix Loop
During `FOCUS_RUNNING`, a background polling loop evaluates telemetry every 1 second. If either a Contextual Distraction Trigger OR a Visual Fatigue Trigger remains constantly true for **15 consecutive seconds**, the application automatically executes the following enforcement sequence:
1. **State Mutation:** Forces the active Pomodoro FSM from `FOCUS_RUNNING` to `FOCUS_PAUSED`.
2. **Viewport Blockade:** Spawns a full-screen, un-dismissible blur overlay modal across the entire application interface reading: *"Focus Interruption Detected. Timer Paused due to Tab Switch or Fatigue."*
3. **Database Logging:** Fires a payload down to `/api/telemetry/distraction` containing the exact timestamp, the active workspace ID, and the distraction type (`TAB_SWITCH` or `FATIGUE_EYE_CLOSURE`).
4. **Release Mechanism:** The user must click a prominent "Re-Engage Focus" button on the modal to clear the blockade and resume the timer loop.

## 4. Machine Learning Model Specifications & Input/Output Vectors
The backend Python engine must process relational tracking tables using scikit-learn and XGBoost to power four specific analytics pipelines.

### Model 1: Session Quality Classifier (Random Forest)
* **Input Vector ($X$):** `[time_of_day, target_session_length, distraction_count_previous_session, rolling_fatigue_index_3_hour]`
* **Target Variable ($Y$):** Binary Classification (`1 = High Quality Completion`, `0 = Fragmented/Aborted Session`).
* **Execution:** Runs right when a user clicks "Start Focus Session". Predicts success probability to let the AI Coach proactively warn the user if conditions are poor.

### Model 2: Timeline Drift Engine (XGBoost Regressor)
* **Input Vector ($X$):** `[current_velocity_hours_per_day, cumulative_days_elapsed, target_hours_remaining, total_distraction_events_logged]`
* **Target Variable ($Y$):** Continuous float representing `Predicted Days of Timeline Drift` (Negative means ahead of schedule, positive means missing deadline by X days).
* **Execution:** Evaluated at the end of every completed focus session in Structured Goal Mode.

### Model 3: Burnout Anomaly Detector (Isolation Forest)
* **Input Vector ($X$):** Daily aggregated rows containing `[total_focus_hours, average_perclos_score, tab_switch_count, break_slippage_latency_seconds]`
* **Operational Mechanics:** Trained entirely unsupervised on a 14-day rolling window of the user's own focus profile rows. 
* **Output:** Returns an anomaly score. If the row maps to an anomaly score outlier contour, the backend flags the user's current status as `HIGH_BURNOUT_RISK`.

### Model 4: Behavioral Archetype Clustering (K-Means)
* **Input Matrix:** Comprehensive 30-day performance matrix.
* **Target:** Groups historical profiles into $K=3$ distinct clusters, which map to user profile archetypes: `[Cluster 0: Morning Peak Performer, Cluster 1: Night-Grinder, Cluster 2: Fragmented/High-Friction Focus]`.
